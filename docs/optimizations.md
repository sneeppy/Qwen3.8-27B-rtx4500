# Чем этот репозиторий отличается от stock vLLM

Девять вещей, которых stock vLLM на этой модели не даёт — сначала коротко, потом подробно — плюс два режима speculative decoding. Цифры tok/s по шагам — в [README](../README.md).

[← к основному README](../README.md)

## Коротко

1. **Обе матрицы эмбеддингов переквантованы** (`prepare/quant_lm_head.py`, `prepare/quant_embed.py`)
   — публичные W4A16 quant оставляют две bf16-матрицы по 2.5 ГБ. Возвращаем 2.6 ГБ.
2. **Двухстрочный патч vLLM**, чтобы код модели реально ходил в quantized embedding kernel (`patches/qwen3_5-embed-quant.patch`).
3. **16-битное recurrent state** — concurrency здесь ограничивает GDN-state, не KV-кэш: до этого из 64 запросов бежало 37.
4. **int8 tensor cores на батчевых GEMM плюс багфикс** — путь W4A8 Marlin в vLLM на этом checkpoint даёт мусор (отрицательные group scales читаются как unsigned); два патча чинят это и делают выбор по слоям.
5. **Дешёвые speculative drafts и draft-словарь по собственным выходам модели** — покрытие 97.5% против 92% у списка с веба; каждый промах — гарантированный reject. Само по себе ~10% single-stream throughput.
6. **Два патча decode-пути на шаге verify** — split-KV attention для multi-query decode (FA2 там простаивает 58 из 82 SM) и sampler top-k/top-p без полной сортировки.
7. **Флаги, которые легко поставить неправильно**, плюс vendored vLLM PR #50021 против illegal memory access в DeltaNet spec-decode ядрах.
8. **Спекуляция, которая читает контекст** — если модель воспроизводит промпт, драфтить из промпта и верифицировать блок длиннее, чем drafter умеет заполнить (`patches/dflash2-lookup-drafting.patch`):
   **381 tok/s** на дословном воспроизведении документа 25k токенов против 260 у первой версии и 159 без неё; lossless.
9. **Prefix caching на гибридной модели** — у апстрима opt-in; `PREFIX_CACHE=1` делает follow-up ход чата по документу 24k ~1 с вместо ~23 с, а 64 запроса с общим system prompt — 17 с вместо 222 с.
10. **int8 prefill в single-user** (`INT8_ACT=int8`) — prefill compute-bound при любом batch size, путь W4A8 на tensor cores даёт +27–30% prefill (+19% на 51k) на стеке dflash2, decode без изменений;
    плюс правка бенч-харнесса (seeded промпты), без которой цифры prefill вообще врут.

## Подробно

1. **Обе матрицы эмбеддингов переквантованы.** У Qwen3.8-27B эмбеддинги untied, поэтому публичные W4A16 несут две отдельные bf16-матрицы по 2.5 ГБ (`lm_head` и `embed_tokens`), которые никто не квантовал. `prepare/quant_lm_head.py` и `prepare/quant_embed.py` переквантовывают обе в int8 group-128 на месте (~0.6% round-trip error, регрессии качества не нашли). Это 2.6 ГБ VRAM обратно.
2. **Небольшой патч vLLM под эти эмбеддинги.** vLLM умеет dequant-on-gather для int-квантованных таблиц, но код модели qwen3_5 к нему не подключён — ни в основной модели, ни в MTP draft-модуле. `patches/qwen3_5-embed-quant.patch` чинит оба места (по две строки).
3. **16-битное recurrent state.** 48 из 64 слоёв — Gated DeltaNet с фиксированным recurrent state на последовательность; конфиг Qwen просит fp32: ~150 МБ на запрос, выделяется заранее, читается и пишется на каждом decode-шаге. На этой архитектуре именно state, а не KV-кэш, режет concurrency: при `--max-num-seqs 64` реально бежало только 37 запросов (строка лога `Running: 37 reqs, Waiting: 27`). `--mamba-ssm-cache-dtype float16` режет объём и трафик пополам; бегут все 64, perplexity до трёх знаков тот же (у fp16 10 бит мантиссы; bf16 с 7 не брали).
4. **int8 tensor cores на батчевых GEMM плюс багфикс.** На 40–64 одновременных последовательностях decode упирается в fp16 tensor-core математику (~63 TFLOPS sustained на 250 W). У vLLM уже есть путь W4A8-INT8 Marlin (`VLLM_MARLIN_INPUT_DTYPE=int8`: веса остаются int4, активации квантуются в int8 на токен, MMA идёт на int8 tensor cores с ~4× скоростью) — но на этом checkpoint он выдавал мусор при красивых бенчмарках. Ядро читает int16-переквантованные group scales как *unsigned*, а у симметричного AutoRound ~50% отрицательных scales. `patches/marlin-int8-negative-scales.patch` складывает знак в int4-коды при загрузке; `patches/marlin-int8-layer-select.patch` позволяет выбрать слои с int8-активациями (и не трогать lm_head с int8-весами, иначе он откажется грузиться).
5. **Дешёвые speculative drafts и словарь, который покрывает то, что модель реально говорит.** Поставляемый MTP draft-модуль — bf16 (850 МБ), и каждый draft-токен ещё гоняет полный lm_head на 248k строк (1.3 ГБ), так что каждый лишний draft стоил ~3 мс, и MTP-3 уже был медленнее MTP-2. `prepare/quant_mtp.py` переквантовывает draft-модуль (int8; у fast-варианта GPTQ int4, `drafter/`), `prepare/build_draft_vocab.py` собирает draft-голову на 40k токенов, `patches/qwen3_5-mtp-draft-vocab.patch` заставляет drafter ею пользоваться. Draft теперь ~0.5–1 мс, четыре штуки окупаются. Список id важнее всего остального в single-user цифрах этого репо: токен вне draft-словаря нельзя предложить — гарантированный reject, ещё и обрывающий цепочку. Поставляемый список (`prepare/draft_vocab_ids.json`) посчитан по 5.4M токенов собственных выходов модели и покрывает 97.5% генерации (96% на коде); прежний веб-список покрывал 92% (83% на коде) и сам по себе стоил 10% single-stream throughput.
6. **Два патча decode-пути на multi-query verify.**
   `patches/spec-decode-attn.patch`: FlashAttention-2 сплитит KV по thread block только когда у запроса один query-токен; у MTP verify их пять, поэтому 24-головая модель гоняет attention на 24 из 82 SM карты 24 ГБ — 57 µs на слой на контексте 1.5k, 1.3 мс на 16k. Маленькое Triton split-KV ядро заменяет это (23 µs / 120 µs). `patches/sampler-small-topk-fast-softmax.patch`: маскирование top-k/top-p в vLLM сортирует весь словарь 248k на каждую строку, softmax — один thread block на строку (140 µs на одну строку ширины 248k, несколько раз за шаг); если top-k ≤ 64 известен на хосте, маска — один `torch.topk`, softmax multi-block, drafts сэмплятся с той же усечённой поддержки, что и target. Вместе +4% на дефолтном sampling.
7. **Подобранные флаги, которые легко поставить неправильно**, каждый описан в launch-скриптах и в gotchas, плюс vLLM PR [#50021](https://github.com/vllm-project/vllm/pull/50021), vendored как `patches/vllm-pr50021-gdn-spec-bounds.patch` (bounds-проверки в DeltaNet speculative-decode ядрах; illegal memory access ловили на нескольких одновременных MTP-запросах).
8. **Спекуляция, которая читает контекст.** Блочный drafter видит окно 2048 токенов; long-context ассистент большую часть выхода воспроизводит то, что ему дали. `patches/dflash2-lookup-drafting.patch` предлагает продолжение самого недавнего более раннего вхождения только что сгенерированного — из любой точки истории этого запроса — с point-mass draft-распределением, чтобы verify оставался точным. Эти токены drafter ничего не стоят, поэтому verify-блок больше не ограничен его семёркой, а длинный блок планируется только пока lookup стреляет: дословное воспроизведение документа 7.83 → 15.0 токенов за шаг, 260 → 381 tok/s.
9. **Prefix caching на гибридной модели — намеренно.** Для mamba/GDN-гибридов vLLM держит это opt-in; `PREFIX_CACHE=1` включает в обоих режимах, recurrent state возобновляется с границы последнего закэшированного блока. Follow-up ходы чата по документу 24k: 23 с → 1 с. 64 API-запроса с общим system prompt 5.8k: 222 с → 17 с.

### int8 prefill в single-user (`INT8_ACT=int8`)

Single-user оставался W4A16, потому что int8-активации на *decode* при batch size 1 ничего не дают — верно, и мимо prefill, который compute-bound при любой concurrency. Torch-профиль 4k prefill на стеке dflash2: 79% времени Marlin GEMM, 15 мс простоя GPU из 2.05 с, так что dtype GEMM — вся игра. `INT8_ACT=int8` (дефолтный набор слоёв `mlp|linear_attn|self_attn`) берёт путь W4A8 из batch-режима на каждый linear, кроме lm_head/embed с int8-весами и MTP-модуля:

| prefill tok/s (dflash2 k=15, PC=1, seeded протокол) | 1k | 4k | 16k | 51k |
|---|---|---|---|---|
| W4A16 (дефолт режима) | 1,437 | 1,494 | 1,410 | 1,200 |
| `INT8_ACT=int8 INT8_LAYERS=mlp` | 1,638 | 1,696 | 1,587 | 1,320 |
| `INT8_ACT=int8` (все linear) | **1,845** | **1,937** | **1,791** | **1,423** |

Decode без изменений (122±5 против 121 tok/s C1 по повторам, 3.2 ток/шаг в обе стороны); качество — задокументированный int8-компромисс: GSM8K 95.0% против 96.5 у fast-варианта, perplexity +4.1% (в основном проза, код плоский), IFBench как в прецеденте batch-режима. Строка 51k выигрывает меньше всего: 16 full-attention слоёв квадратично растут до ~40% prefill, а у FA2 на head_dim 256 на sm86 нет более быстрого варианта (FlashInfer в пределах 1.5%, и он ломает split-KV verify на decode).

**int8-QK prefill attention** (`PREFILL_ATTN=int8`, `patches/prefill-attn-int8.patch`) бьёт по тому, что осталось после GEMM: 16 full-attention слоёв, у которых head_dim 256 держит FA2 на 54–57 TFLOPS на sm86 (85% практической fp16 mma карты — никакой fp16-переписывание не выиграет). Triton-ядро гоняет QK^T на int8 tensor cores с 2× скоростью fp16, в духе SageAttention: K сглаживается per-head channel mean (инвариант softmax, точно до округления int8 — cos > 0.99999 vs fp32 на 4–51k), собирается и квантуется один раз на layer-chunk в сплошной int8 scratch; у строк Q — per-row scales; P.V остаётся bf16. На самом attention это 1.27× FA2 на 4k и до 1.35× на 51k; end-to-end с `INT8_ACT` добавляет +2.7% на 16k и +5.3% на 51k (1,839 / 1,498 tok/s), decode без изменений.
В одиночку почти ничего не даёт — это структура, не дефект: prefill без int8 GEMM доминирован GEMM, быстреему attention почти нечего выигрывать. Замер standalone на reference-боксе (`bench/prefill_ab.sh`, два чередующихся плеча на условие, каждое воспроизводится до 0.1%): 1,167 / 1,126 / 1,012 tok/s на 4k / 16k / 51k против 1,164 / 1,114 / 980 stock — +0.3%, +1.1%, +3.3%, выигрыш растёт с контекстом ровно как доля attention. На WSL2 та же standalone-ячейка была на 1–6% отрицательной ([#62](issue #62)), поэтому `PREFILL_ATTN` в одиночку считать шумом-чуть-плюсом и парить с `INT8_ACT`, где то же ядро сверху даёт +1.8% на 16k и +4.5% на 51k (1,826 / 1,491 против 1,793 / 1,427).
По конструкции только prefill: ветка срабатывает на single-request prefill-чанки на точной serving-геометрии, иначе fall-through в FA2.

Что в этой кампании измерили и **не** окупилось — чтобы никто не ходил тем же кругом:

- **Бенч-харнесс врал prefill.** У `vllm bench serve` дефолт `--seed 0`, каждый вызов крутит те же промпты; с `--enable-prefix-caching` поздние вызовы получают тихие частичные prefix-hit, размер которых зависит от геометрии пула сервера. Старый протокол одну конфигурацию занижал на 15–20%, другую завышал в 3× (16k prefill «измеренный» за 4.0 с, вхолодную стоит 11.2 с). `bench/run_benchmarks.sh` теперь сидит каждый вызов; таблицы выше — seeded цифры, старые опубликованные строки prefill несравнимы.
- **`SPEC=off` prefill ~на 20% медленнее `SPEC=dflash2`** — снятие drafter роняет сервер с V2 model runner на V1. Собственная цена prefill drafter на V2 runner нулевая (6 запусков ядер в профиле 4k); цифра «~15% TTFT», которая тут ходила, старше fused context-KV precompute.
- **`PREFIX_CACHE=0` prefill ~на 20% медленнее `PREFIX_CACHE=1`** на этом стеке; align mode как причина исключён (PC=0 + `--mamba-cache-mode align` меряется как обычный PC=0). Не выключайте кэш «ради скорости».
- **Больше prefill-чанки не стартуют** при закреплённом `KV_MEM`: `--max-num-batched-tokens` 4096 и 8192 раздувают профильный пик активаций выше transient floor (init движка падает). 2048 остаётся.
- **Тюнинг тайлов Marlin для W4A8 GEMM end-to-end смывается.** Standalone-свип (min-of-rounds, burst clocks) показывает +2–20% на GEMM против stock-тайлов при M=2048 — и ровно +0.4% end-to-end, потому что throttling 250 W сглаживает то, что видно в burst. `patches/marlin-tune-table.patch` всё равно кладёт проводку (выключено по умолчанию, `VLLM_MARLIN_TUNE=1`) для карт без power cap.
- `INT8_LAYERS="mlp|linear_attn"` (середина: только GDN) падает на первом forward — баг inductor codegen на смешанном наборе на этом пине torch/vllm. Берите `mlp` или полный дефолт.

### DFlash2 (`SPEC=dflash2`)

После всего выше рычаг остался один — acceptance, а MTP-голова Qwen — однослойный chain drafter на потолке. [DFlash2](https://inco.ai/blog/dflash2/)
(Inco, авг 2026) — другой drafter под ту же цель:
5 слоёв в стиле Qwen3, которые предсказывают весь блок из 7 токенов одним неавторегрессивным проходом по hidden states слоёв target 5/19/33/47/61, плюс селектор, который идёт по согласованному пути через 16 кандидатов на слот. На bf16-модели заявляют 4.80 токенов за шаг против 4.28 у MTP при том же размере блока. Что понадобилось, чтобы это окупилось на карте 24 ГБ, по порядку:

1. **Нативная поддержка плюс порт репо.** Поддержка в vLLM — [PR #52816](https://github.com/vllm-project/vllm/pull/52816), нативно в v0.28.0 на V2 model runner. Старый `patches/dflash2-backport.patch` на этом теге снят; поверх native 0.28.0 лежат `patches/dflash2-lookup-drafting.patch` и `patches/dflash2-ngram-chains.patch` — квантованная candidate head, context lookup и удлинение цепочек без drafter. Порт DFlash2 ещё шарит *квантованный* lm_head target (апстрим отказывается), а V2 sampler берёт наш sort-free small-k путь top-k/top-p. Режим MTP не тронут (перемерили: 110.7 / 113.4 tok/s, пул 73 777 токенов).
2. **Сам drafter — 1.92B параметров, 3.85 ГБ в bf16** — читается раз за шаг, это +5 мс на GPU 24 ГБ и нулевой выигрыш (106 / 112 tok/s, замер), плюс пул KV 21k токенов. `drafter/capture_dflash2.py` хукает linear-слои drafter внутри vLLM на 400 реальных промптах (~290k строк на слой, плюс распределение входа context-KV precompute для строк k/v), `drafter/quant_dflash2.py` GPTQ-квантует 36 матриц в W4A16 compressed-tensors (Marlin): **1.19 ГБ**, выложен как [syvai/Qwen3.8-27B-DFlash2-W4A16](https://huggingface.co/syvai/Qwen3.8-27B-DFlash2-W4A16)
   (`prepare/fetch_dflash2.py`). int4 стоит ~5% acceptance на дефолтном sampling (3.2 против 3.4 токена за шаг) и ничего на greedy; оставить `fc` в bf16 это не вернуло.
3. **Результат** (`bench/run_benchmarks.sh single`, fast-вариант target): 26.5 мс на шаг против 24.8 у MTP, 3.14–3.34 токена за шаг против 2.8–2.9 → **117.8 tok/s на дефолтном sampling и 125.7 greedy на C1** (MTP: 111–115 / 115–124), лучшие прогоны этого drafter 133.8 / 138.5, плюс выше decode на C2–C8. То же выходное распределение по конструкции (perplexity 8.094, GSM8K 96.0–96.5%).

4. **Вернуть контекст к 64k** понадобился второй патч (`patches/hybrid-kv-groups-v2-cudagraph.patch`): первая версия режима упиралась в 40k. vLLM размечает KV-группы гибридной модели по *самому маленькому* ведру слоёв одного типа — с drafter это его 5 sliding-window слоёв, поэтому 16 attention-слоёв target паддились до 20, а 48 GDN — до 50: +25% пула на каждый токен контекста ради слоёв, которые не были проблемой. Sliding-window группы держат только window блоков, паддить *их* стоит ~7 МБ на запрос. Пул с 105 до 78 КБ на токен (MTP: 75), т.е. 45 383 токена на 40k → 69 758 на 64k. Тот же патч делает память CUDA-графов V2 runner явной (`VLLM_V2_CUDAGRAPH_MEM_MIB`): у апстрима возвращается 0, поэтому ~1.2 ГиБ графов садятся сверху `--gpu-memory-utilization` — просишь 0.93, живёшь на 0.98. Поскольку профильный пик активаций runner ещё гуляет ~1 ГиБ между стартами, этот режим пинит пул в байтах (`KV_MEM`, 5.2 ГиБ), а не utilization; старт тогда детерминирован (69 758 токенов дважды).

### Драфт из контекста (`LOOKUP=1`)

Drafter читает окно 2048 токенов. Long-context ассистент большую часть выхода *воспроизводит* — цитата документа, список команд, переписывание абзаца с сохранением кода — и эти токены лежат дословно в промпте, на десятки тысяч токенов дальше, чем drafter видит. `patches/dflash2-lookup-drafting.patch` сканирует собственную историю токенов запроса (буфер, который vLLM и так держит) на самое недавнее вхождение самого длинного суффикса уже сгенерированного и предлагает токены, которые за ним следовали — одна Triton-программа на запрос, независимо от batch size, с reject-тестом `NMIN` токенов до удлинения кандидата. Остаётся lossless: greedy-верификация draft-распределение не читает, на каждую позицию, которую заполнил lookup, ставится point mass на предложенный токен — легальное предложение для rejection sampler vLLM (acceptance становится p(x), residual из того же буфера).

Что решает, сколько это стоит, — четыре вещи.

**Verify-блок больше не обязан быть блоком drafter.** `dflash_config.block_size` — свойство checkpoint (8 = якорь плюс 7 mask-токенов, на которые учили DFlash2), и vLLM делал его ещё и длиной verify у target, так что дословная копия никогда не могла превысить 8 токенов за шаг. Она сидела на этом потолке: 7.83 из 8 принято при воспроизведении первых 60 строк документа. Теперь drafter держит свой блок, а target верифицирует более длинный (`DFLASH_TOKENS`); позиции за блоком drafter заполняются из контекста. Drafter они ничего не стоят — без лишних mask-токенов и без лишнего прохода candidate head: контекст — бесплатный источник drafts, drafter — нет.

**Длинный блок планируется только пока идёт копирование.** Каждая лишняя позиция verify стоит около 1 мс attention на контексте 25k, поэтому speculator на каждом шаге сообщает, сколько предложений scheduler реально должен выставить на проверку: обычно 7 у drafter, весь блок когда (a) у lookup есть match с запасом токенов на хвост и (b) только что закончившийся шаг выдал не меньше полного короткого блока — два раза подряд. Один насыщенный шаг бывает внутри обычной прозы, купленный блок впустую; два подряд — копия. Флаги читаются из pinned-копии, которая приехала асинхронно, на шаг устарела: синхронное чтение — device synchronize на каждом decode-шаге, замер 5%, больше, чем длинный блок стоит на большинстве работы. vLLM отдаёт счётчик drafts scheduler только на синхронном scheduling-пути, поэтому этот режим идёт с `--no-async-scheduling`; на batch 1 это меньше 1%.

Против того же сервера с выключенным длинным блоком триггер — выигрыш на каждой задаче сюиты: +55% воспроизведение документа, +10% переписывание, +2–3% проза.

**Предложение сливается с drafter, а не подменяет его.** Match не короче `VLLM_DFLASH2_LOOKUP_NSTRONG` (8) токенов берётся сам; короче — только если drafter независимо предложил те же первые `_AGREE` (2) токена. Два независимых источника согласны — дешёвый сигнал уверенности (drafter смотрел на hidden state, lookup — на текст) и то, что останавливает случайный 6-токенный match от порчи acceptance на прозе, как делала первая all-or-nothing версия.

**Match может пересекаться с суффиксом, который он матчил**, поэтому повторяющийся паттерн (маркер списка, отступ, fence) предлагается из своего периода, а не пропускается.

Замер на контексте 25k, greedy, против того же сервера с предыдущей версией (токенов за шаг / decode tok/s):

| | без lookup | дефолт (`DFLASH_TOKENS=7`) | `DFLASH_TOKENS=15` |
|---|---|---|---|
| воспроизвести первые 60 строк дословно | 4.72 / 159 | 7.83 / 260 | **14.97 / 381** |
| укоротить, команды оставить | 2.70 / 90 | 3.19 / 107 | **3.50 / 113** |
| процитировать и объяснить | 3.01 / 101 | 3.21 / 107 | **3.35 / 110** |
| воспроизвести каждую команду | 4.62 / 153 | 5.23 / 173 | 5.32 / 166 |
| свободное резюме / Q&A | 2.15 / 72 | 2.08 / 69 | **2.13 / 71** / 2.01 / 67 |
| C1, 8 коротких чат-промптов | 3.22 / 126 | 3.33 / 131 | **3.42 / 133** |

Длинный блок стоит **+47%** там, где модель воспроизводит контекст, и несколько процентов на остальной работе, когда планируется только во время реальной копии. Поставляется как режим — `DFLASH_TOKENS=15`, для coding-ассистента с правками или RAG, который цитирует источники, — потому что ещё стоит 4 слота запросов вместо 8 и 56k контекста вместо 64k. Качество то же: GSM8K 96.5% (200 вопросов, greedy) с lookup, как без него; 7 из 9 длинных greedy-промптов побайтно совпадают с тем же сервером при `LOOKUP=0` (два отличающихся — near-tie флипы, gotcha 14).

Режим также стоит 4 слота вместо 8 и 56k контекста вместо 64k, потому что `--mamba-cache-mode align` резервирует страницы recurrent state на слот на speculative-блок.

Парьте с `PREFIX_CACHE=1` (гибридный prefix caching vLLM, opt-in у апстрима): follow-up ход по документу 24k токенов стоит **~1 с вместо ~23 с**, потому что attention KV переиспользуется, а recurrent state возобновляется с границы последнего закэшированного блока, за одну лишнюю страницу state на запрос (~16% пула KV). Prefill перестаёт доминировать чат, и тогда драфт из контекста делает decode быстрым.

`PREFIX_CACHE=1` работает и в **batch-режиме**, и там не менее важен: 64 запроса с одним system prompt 5820 токенов занимают 222 с без него и **16.9 с** с ним (медиана латентности 94.9 с → 8.0 с), за ~14% пула KV и без изменений на нагрузке без общего префикса. Если API-бэкенд шлёт одни и те же инструкции с каждым запросом — это самая большая вещь в репозитории для вас. (Остальные три изменения на этой странице — lookup drafting, фикс KV-групп и учёт графов V2 — срабатывают только на пути DFlash2 и в batch inert.)

Ограничения по памяти и окну: каждый *resident* запрос держит 1+7 слотов recurrent state — 0.88 ГиБ, 15.8% пула `CTX=fast`, ещё до любого контекста — поэтому шесть запросов resident, седьмой preempted, против восьми у MTP с 0.44 ГиБ; с 8 одновременных длинных генераций e2e у MTP снова выше (309 против 235 tok/s). Окно attention drafter 2048 токенов отдельно теряет acceptance на long-context задачах (2.3–2.6 против 2.6–3.0 токена за шаг на 12–36k, где MTP на 5–10% впереди e2e). `CTX=long`/`huge` остаются MTP.

Это не только про память, хотя раньше в этом абзаце так и было написано. Per-stream decode жёстко падает с concurrency — 137 / 97 / 46 tok/s на 1 / 2 / 4 разных 4k-потоках — потому что каждый resident запрос добавляет ~7 мс к forward (25.9 → 49.1 мс). Суммарный throughput всё равно растёт (137 → 309 tok/s), никто не preempted, значит verify батчится; падает латентность на пользователя. MTP делает то же (126 / 103 / 46 на поток, ~5 мс на resident), так что это гибридная модель плюс спекуляция на одной GPU 24 ГБ, а не ошибка DFlash2. Своё у DFlash2 — кончаются страницы state на пяти resident, где MTP держит восемь и доходит до 383 tok/s aggregate на C8. Для **одного человека** с обычным контекстом — то, ради чего single-user — это самый быстрый конфиг в репозитории.
